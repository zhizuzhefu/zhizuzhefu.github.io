怎么验收 AI 写的代码？

AI 一次写出几千行代码，已经没人读得完。逐行审查成了形式，真正要回答的是：它做的事，是不是我要的事？下面是一套不依赖读代码的验收方法：写下你自己的验收标准，真的跑一遍，用证据决定收不收。

为什么只看 diff 不够

  • 代码量超出了人能认真读完的范围，评审容易变成“看着没问题”。
  • AI 写的测试和实现往往出自同一次推理：理解错了，两边会一起错，测试照样全绿。
  • “能跑起来”不等于“符合需求”。需求里的细节，只有写成可执行的期望才会被真正核对。

独立验收的四条原则

  1. 独立于实现。从接口边界和界面外部去验，不依赖被测代码的内部结构，也不由写代码的那一方来定标准。
  2. 标准由你定。期望值来自需求，而不是来自 AI 生成的代码。你说“订单创建后状态是 pending”，用例就这样写。
  3. 要有证据。请求与响应记录、界面每一步的截图，比一句“我检查过了”可靠，也能转发给别人看。
  4. 可重复，并对应版本。同样的用例每次得到同样的结论，并且知道它验的是哪一次提交。

接口验收清单

  • 状态码之外，断言响应体里的关键字段，不要只看到 200 就算过。
  • 错误路径：未登录、参数缺失或错误、重复提交，返回的应该是什么。
  • 权限：换一个账号，能不能看到不该看到的数据。
  • 数据副作用：创建之后能查到，删除之后查不到，用流程把几个用例按顺序串起来。
  • 边界：空列表、分页末页、最大长度、特殊字符。

界面验收清单

  • 把关键路径从头走到尾：登录、下单、看到订单。
  • 断言用户能看到的结果（标题、文案、数量），而不是某个元素“存在”。
  • 按人看到的样子找元素：名叫“登录”的按钮、标签是“手机号”的输入框，比 CSS 选择器耐改版。
  • 每一步留截图，失败时保存页面、控制台和网络请求，人眼扫一遍就能发现不对。
  • Web 和 Android 都要验的话，放进同一个项目里，用同一套方式管理。

用 requestbaby 落地

requestbaby 把上面的原则做成了工具：用例是 JSON 文件，运行时不调用大模型，结论由你写下的断言决定。最短的一条路径：

requestbaby init myapi && cd myapi
requestbaby vars set baseUrl http://localhost:8080 -e dev
requestbaby new case collections/orders 创建订单 -m post
requestbaby send collections/orders/01-创建订单.json --suggest   # 看真实响应，按字段写断言
requestbaby run                                                  # 跑全部用例
requestbaby verify -e dev --report html                          # 校验 + 全部用例 + 全部流程，生成报告

让 AI 帮你写用例时，先让它读 requestbaby guide（一页写法速查），写完用 requestbaby validate 检查。requestbaby verify 的退出码 0 表示全部通过、1 表示有用例失败、2 表示无法完成验证，可以直接放进 CI。

几个常见的坑

  • AI 为了让用例通过而改用例。把用例文件放进版本库，评审用例的 diff：它比读实现代码轻松得多，断言被放宽一眼就能看出来。
  • 断言写得太松。用 send --suggest 看一次真实响应，按字段写断言，而不是只断言状态码。
  • 只测顺利的那条路。错误路径和权限问题，恰恰是 AI 最容易漏的地方。
  • 忽略时过时不过的用例。同一个提交上结果不稳定的用例会被标成“不稳定”，先找出原因再信任它的结论。

How do you accept AI-written code?

AI can produce thousands of lines at once and nobody reads them all. Line-by-line review becomes a formality, and the real question is whether what it built is what you wanted. Here is a way to accept work without reading every line: write your own acceptance criteria, run them for real, and decide on evidence.

Why reading the diff is not enough

  • The volume is beyond what a person can read carefully, so review drifts into “looks fine”.
  • Tests and implementation written by AI often come from the same reasoning. If it misunderstands the requirement, both are wrong together and the tests still pass.
  • “It runs” is not “it meets the requirement”. Details only get checked once they are written as executable expectations.

Four principles of independent acceptance

  1. Independent of the implementation. Check from the API boundary and the UI outside. Do not rely on the code’s internals, and do not let the author set the bar.
  2. You own the criteria. Expected values come from the requirement, not from generated code. If a new order should be pending, the case says so.
  3. Keep evidence. Recorded requests and responses and a screenshot of every UI step beat “I checked it”, and can be forwarded to others.
  4. Repeatable and tied to a version. The same case gives the same verdict every time, and you know which commit it verified.

API acceptance checklist

  • Assert the key fields in the response body, not just a 200 status.
  • Error paths: not logged in, missing or invalid parameters, duplicate submissions. What should come back?
  • Permissions: can another account see data it should not?
  • Side effects: created records can be fetched, deleted ones cannot. Chain the cases in order as a flow.
  • Edges: empty lists, the last page, maximum lengths, special characters.

UI acceptance checklist

  • Walk the key path end to end: log in, place an order, see the order.
  • Assert what a user can see (headings, text, counts), not that an element merely exists.
  • Find elements the way a person sees them: the button named “Log in”, the input labelled “Phone”. This survives redesigns better than CSS selectors.
  • Keep a screenshot of each step, and save the page, console and network requests on failure. A quick look often spots what is wrong.
  • If you need both Web and Android, keep them in one project and manage them the same way.

Putting it into practice with requestbaby

requestbaby turns these principles into a tool: cases are JSON files, no model is called when running, and the verdict comes from the assertions you wrote. The shortest path:

requestbaby init myapi && cd myapi
requestbaby vars set baseUrl http://localhost:8080 -e dev
requestbaby new case collections/orders create-order -m post
requestbaby send collections/orders/01-create-order.json --suggest   # see the real response, assert per field
requestbaby run                                                  # run every case
requestbaby verify -e dev --report html                          # validate + all cases + all flows, write a report

When you want AI to write cases, have it read requestbaby guide (a one-page cheat sheet) first and check the result with requestbaby validate. The exit code of requestbaby verify is 0 when everything passed, 1 when a case failed and 2 when verification could not complete, so it fits straight into CI.

Common pitfalls

  • AI edits the cases to make them pass. Keep case files in version control and review their diffs. That is far lighter than reading the implementation, and a loosened assertion is easy to spot.
  • Assertions that are too loose. Use send --suggest to look at a real response and assert per field rather than only the status code.
  • Only testing the happy path. Error paths and permissions are exactly what AI tends to miss.
  • Ignoring flaky cases. A case that passes and fails on the same commit is flagged as flaky. Find out why before trusting its verdict.

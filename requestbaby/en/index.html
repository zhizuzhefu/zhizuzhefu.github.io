AI writes more code than anyone can read.

Line-by-line review can no longer keep up with what AI produces. Trust has to come from somewhere else: acceptance criteria you own, independent of the implementation, and evidence you can reproduce. That is what requestbaby provides, so a person can accept an AI delivery with something solid to point to.

Independent of the code.

Cases are plain JSON and check from the API boundary and the UI outside, not from inside the code. AI can read and write them, but the assertions are yours and cannot be quietly loosened.

APIs and UIs, together.

HTTP / HTTPS, gRPC and WebSocket APIs, web pages and Android apps live in one project. Assert status, headers and any response field, and capture a login token as a variable for later steps.

Evidence for every step.

Every UI step is captured with the target boxed. On failure the page, console and network requests are saved too. History is tied to the commit, and cases that pass and fail on the same commit are flagged as flaky.

Same case, same verdict.

No model is called to judge a result, so no tokens are spent. The CLI exit code is the verdict and one command fits into CI. It is a single executable with no runtime dependencies.

Every verdict comes with evidence.

When an API case fails, you see what was asserted, what was expected and what actually came back. Every UI step has a screenshot with a red box around what was clicked or checked.

What it can check.

APIs

HTTP / HTTPS, gRPC (server reflection or .proto files, no code generation) and WebSocket (send, receive and assert step by step). Separate addresses and accounts for dev / test / prod, with secrets kept in local files outside version control. Chain collections into flows or repeat a case over several data sets.

Web UIs

Drives your local Chrome or Edge directly, with no Playwright or Node, or connects to a remote browser in Docker or the cloud. Find elements the way a person sees them (the button named “Log in”, the input labelled “Phone”) and rely on auto-wait instead of sleeps.

Android apps

Operate real devices or emulators through adb, including remote emulators and cloud phones. Locate by role and text as on the web, and keep the view hierarchy and logcat on failure.

What you already have

Import existing endpoints from OpenAPI / Swagger / Postman / cURL. Route all outbound traffic through one proxy (socks5 / http), or switch it off with a click.

Everything for everyday API calls.

You can start by using it as a handy API client. There is nothing about “acceptance” to learn first.

  • Build requests with forms: any method, query parameters and headers, with JSON, form, form-data file upload and raw text bodies.
  • Read the response: status, time, body (formatted / raw), headers, and the equivalent cURL.
  • Environments and variables: one set of addresses and accounts for dev / test / prod, tokens captured from a login and reused, cookies saved automatically.
  • Collections and bulk runs: group cases in folders, write shared headers once, run everything with one click and see every result.
  • Import existing endpoints from cURL, Postman and OpenAPI / Swagger.

Quick start

A case is just a JSON file.

Cases live under collections/ and run in file-name order. This one POSTs to /auth/login on baseUrl, expects status 200, code equal to 0 and a string data.token, then stores the token so later cases can use {{token}}. On failure the report says exactly what differed: body.code = 0 → expected 0, got 4030001.

{
  "name": "Log in",
  "request": {
    "method": "POST",
    "url": "{{baseUrl}}/auth/login",
    "body": { "json": { "username": "{{username}}", "password": "{{password}}" } }
  },
  "expect": {
    "status": 200,
    "body": { "code": 0, "data.token": { "type": "string" } }
  },
  "capture": { "token": "data.token" }
}

UI cases look similar, with the request replaced by steps. For Android, swap web for android and give the app package and steps:

{
  "name": "Log in and see orders",
  "web": {
    "url": "{{webBase}}/login",
    "steps": [
      { "fill": { "label": "Phone" }, "value": "{{phone}}" },
      { "fill": { "label": "Password" }, "value": "{{password}}" },
      { "click": { "role": "button", "name": "Log in" } },
      { "expect": { "role": "heading", "name": "My orders" } }
    ]
  }
}

Light to start. Three steps to evidence.

  1. Write the expectations

    Write them yourself, or have AI read the one-page requestbaby guide and write them for you. cURL, OpenAPI and Postman can be imported too.

  2. Run it for real

    requestbaby run runs every case; requestbaby verify validates, runs cases and flows, and returns one verdict.

  3. Read the evidence, decide

    Open the desktop app or the HTML report to see responses and per-step screenshots, then accept or send the work back.

requestbaby init myapi && cd myapi                          # scaffold a project: dev / prod envs, sample case
requestbaby vars set baseUrl http://localhost:8080 -e dev   # tell it where the service under test lives
requestbaby send collections/orders/01-create-order.json --suggest   # send once, see the real response, get assertion hints
requestbaby run                                             # run every case
requestbaby open                                            # open the project in the desktop app

The CLI and the desktop app read and write the same project directory, and every action in the app has a matching command.

Who it is for.

  • People who let AI write backend or frontend code and want their own acceptance criteria instead of reading every line.
  • Teams that want API and UI checks in CI.

Before you start

What is requestbaby for?

AI now writes more code than anyone can read line by line. requestbaby lets you keep your own acceptance criteria: write what to send, what to click and what should come back as JSON, run it for real, and use the pass/fail result, recorded responses and per-step screenshots to decide whether to accept a delivery.

How is it different from Postman or Playwright?

Those are development tools; requestbaby sits on the acceptance side. Cases are plain JSON, independent of the code under test, and easy for both people and AI to read and write. APIs and UIs are checked in one project, and every verdict comes with evidence. Postman, OpenAPI and cURL can be imported. UI checks drive your local Chrome or Edge directly, with no Playwright or Node to install.

Can I just use it for everyday API calls, like Postman?

Yes. The desktop app builds requests with forms (method, parameters, headers, JSON / form / file-upload bodies) and supports environment variables, token passing, cookies, collections, bulk runs and import from cURL / Postman / OpenAPI, with no JSON to write. See the quick start.

Does it call an LLM to decide pass or fail?

No. The verdict comes only from the assertions you wrote. No model is called, no tokens are spent, and the same case gives the same answer every time.

Is it free? Does it upload my data?

Free and open source under the MIT license. Cases, responses, screenshots and history stay in your own project directory. There is no account and no usage analytics. See the privacy notes.

Which platforms are supported?

The desktop app runs on macOS 12 or later (signed and notarized by Apple). The CLI runs on macOS (Apple silicon and Intel) and Linux (x86_64 and arm64) and fits into CI.

How do I run it in CI?

Run requestbaby verify: it validates, runs every case and every flow. Exit code 0 means all passed, 1 means a case failed, 2 means verification could not complete. Add --report json or html for a report.
